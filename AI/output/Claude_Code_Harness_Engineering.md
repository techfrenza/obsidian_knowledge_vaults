
## 一、核心概念：什么是线束工程？

**线束工程（Harness Engineering）** 是指为 AI 模型构建基础设施、工具集和运行环境，使其能够在特定领域中有效地作为自主智能体运行的工程实践。

一个常见的误解是：围绕模型编写的"框架代码"才是智能体。正确的视角恰恰相反：

- **模型（Model）= 智能体（Agent）= 驾驶员**：感知环境、推理目标、决定行动。
- **线束（Harness）= 车辆**：为驾驶员提供工具、知识和边界约束。

线束工程师的目标不是让模型"变聪明"——模型已经具备智能——而是**构建一个高质量的运行世界**，让既有的智能得以有效表达。

---

## 二、线束工程师的五项核心工作

传统的"提示词堆砌（Prompt Plumbing）"——用复杂的 if-else 分支和链式提示词来"编程"AI 行为——已被证明脆弱且难以维护。线束工程师转而专注于以下五个领域：

| 工作领域 | 内容 |
|---|---|
| **实现工具（Tools）** | 赋予智能体"双手"：文件读写、Shell 执行、数据库查询、API 集成 |
| **策划知识（Knowledge）** | 提供领域专业知识供按需调用：架构指南、产品文档、合规要求 |
| **管理上下文（Context）** | 提供"干净的记忆"：子代理隔离复杂任务、适时压缩上下文、跨会话持久化目标 |
| **控制权限（Permissions）** | 设置护栏和安全边界：沙箱环境、危险操作需人工审批、信任边界强制执行 |
| **采集任务轨迹（Data）** | 记录智能体感知与行动的过程数据，作为未来模型微调的训练信号 |

## 三、有效线束的关键组成（以 Claude Code 为例）

Claude Code 本身就是一个设计优雅的线束，其核心组件包括：

1. **主循环（The Loop）**：模型持续接收输入、推理、执行工具的闭环。
2. **内置工具（Built-in Tools）**：`Bash`、`Read`、`Edit` 等基础能力。
3. **持久化上下文（Persistent Context）**：`CLAUDE.md` 文件存储项目级指令，每次对话均会重新加载。
4. **技能扩展机制（Skills）**：通过 `.claude/skills/` 目录按需加载领域知识，不会污染主循环上下文。

> **官方文档确认**：各扩展机制分工明确——`CLAUDE.md` 处理常驻上下文，Skills 管理按需知识，MCP 处理外部连接，子代理提供任务隔离，Hooks 实现自动化。有效的线束配置会根据具体工作流需求组合使用这些功能。

## 四、第一阶段：建立线束基础

### 4.1 建立系统记录（System of Record）

在编写任何代码之前，先固化 Claude 的行为边界。

**创建 `AGENTS.md`（核心原则文件）**：

- 建议控制在 100–300 行，防止信息过载。
- 写入"金色原则（Golden Principles）"：不可商量的架构规则，例如：
  - "严格执行分层架构（Types → Service → UI）"
  - "优先使用共享工具包，严禁编写重复的本地辅助函数"
  - "代码提交前必须通过所有单元测试"

**创建 `CLAUDE.md`（CLI 专属记忆）**：

Claude Code 每次收到消息时都会重新加载此文件。最佳实践是通过软链接保持同步：

```bash
ln -sfn AGENTS.md CLAUDE.md
```

**模块化规则**：在 `.claude/rules/` 目录下创建主题规则文件（如 `testing.md`、`api-conventions.md`），并通过 YAML 前注中的 `paths` 字段实现条件加载，节省上下文预算。

**全局偏好**放 `~/.claude/CLAUDE.md`，**项目标准**放根目录，**模块专属规则**放子目录。

### 4.2 配置物理阻挡：Hooks（钩子）

> **重要区别**：`CLAUDE.md` 是建议性的（模型可能偏离），而 **Hooks 是确定性的**——它们 100% 会被执行，是真正的物理约束。

编辑 `.claude/settings.json`：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "/path/to/scripts/validate-bash.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint && npm run typecheck"
          }
        ]
      }
    ]
  }
}
```

- **`PreToolUse`**：拦截高风险命令（如 `rm -rf`、`git push --force`）。
- **`PostToolUse`**：每次编辑后自动运行 Linter/类型检查；若检查失败，错误回传给 Claude 强制修复——形成**自我纠错循环**。
- **`SessionStart`**：在会话开始时注入环境变量或最新上下文（如当前待处理 Issue 列表）。

> **官方文档确认**：权限规则由 Claude Code 强制执行，而非由模型本身执行。提示词或 `CLAUDE.md` 中的指令只影响 Claude 的意图，不改变 Claude Code 实际允许的操作。访问权限通过 `/permissions`、权限模式或 `PreToolUse` 钩子来授予或撤销。

### 4.3 增量授权（Incremental Autonomy）

- **初始阶段**：仅授予只读 + 测试运行权限。
- **观察 3–5 个成功的任务循环后**：再逐步开放文件写入和 Git 操作权限。

可在 `.claude/settings.json` 中设置默认权限模式：

```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

### 4.4 减少上下文噪声

创建 `.claudeignore` 文件排除 `node_modules`、编译产物和日志，减少无效 token 消耗。

## 五、第二阶段：标准开发工作流——四阶段闭环

对于任何涉及多文件的复杂任务，遵循 **Plan → Execute → Verify → Repair** 闭环：

### 5.1 Plan（计划阶段）

- **操作**：通过 `--permission-mode plan` 启动，或在会话中按 **Shift+Tab** 切换到计划模式。
- **Claude 在此阶段不修改任何代码**，只进行调研和规划。
- **要求 Claude 输出**：
  - 复述总体目标（确认理解无误）
  - 详细执行步骤及架构影响
  - 受影响的文件清单
  - 测试策略
- **人工审查**：开发者快速审阅计划（通常 1–2 分钟），确认无误后授权进入下一阶段。

```bash
claude --permission-mode plan
```

### 5.2 Execute（执行阶段）

- 退出计划模式，告知 Claude"按计划执行"。
- **原子化/增量式构建**：先写 Schema → 再写 API → 最后加验证，每步对齐目标。
- **手术式修改原则**：只修改计划中指定的代码，拒绝未请求的重构，保持方案最简化。

### 5.3 Verify（验证阶段）

> **核心原则**：验证必须独立于实现。不能只听信 Claude 的口头报告，必须以实际运行结果为准。

- 通过 `/clear` 开启全新会话，或调用专门的子代理（Subagent）担任独立评估者，防止生成背景产生误导。
- **验证顺序**：
  1. **确定性检查优先**：Linter → 类型检查 → 单元测试（PostToolUse Hook 可自动触发）
  2. **视觉评审**：UI 改动要求截图对比
  3. **LLM-as-Judge**：使用另一模型评估架构一致性等定性指标

### 5.4 Repair（修复阶段）

- 将完整的错误日志和栈追踪喂回给 Claude，要求分析根因而非盲目重试。
- **沉淀规则**：若某类错误反复出现，明确要求 Claude 将修复偏好写入 `CLAUDE.md`：

  > "Update CLAUDE.md so you don't make that mistake again."

- 重复"验证-修复"循环，直到通过所有质量门禁。

## 六、核心架构：评估者-优化者（Evaluator-Optimiser）

为提升闭环效果，推荐多模型异构分工：

| 角色 | 模型建议 | 职责 |
|---|---|---|
| **Generator（生成者）** | Sonnet | 创意产出、代码实现 |
| **Evaluator（评估者）** | Opus | 批判性评审、逻辑验证 |

这种"代理对代理"的对抗模式能显著降低幻觉率，确保交付物符合生产级工程标准。

## 七、上下文与 Token 治理

上下文窗口是最昂贵的资源，必须主动管理以防模型"变笨"。

| 操作 | 时机 | 目的 |
|---|---|---|
| `/compact` | Token 占用达 60–70% | 压缩对话摘要，保留架构决策，释放预算 |
| `/clear` | 任务切换时 | 清除脏上下文，防止污染新任务 |
| 即时检索（Grep/Glob） | 需要读取代码时 | 动态按需读取，而非一次性加载整个代码库 |
| 子代理（Subagents） | 大规模调研或全量测试时 | 隔离噪声，主会话只接收简洁摘要 |

## 八、长期维护：防止"AI 废料"堆积

AI 生成速度极快，若不主动管理，技术债会迅速累积。

### 8.1 自动化"园丁"机制

- **文档园丁（Document Gardener）**：定期扫描文档与代码行为的一致性，发现偏差时自动提交修复 PR。
- **重构智能体（Refactoring Agent）**：作为后台任务运行，识别并修复违反"金色原则"的代码模式。

### 8.2 开发者反馈强化（RLDF）

当人工修复 AI 代码或拒绝 PR 时，明确要求 Claude 将该偏好写入配置文件，形成**组织级复利**：

```
将此修复偏好加入 CLAUDE.md 的金色原则中
```

### 8.3 并行 Agent 团队

对于大型重构，使用 git worktree 开启多个并行会话，让子代理在独立工作树中处理不同模块：

```bash
claude -w  # 在新的 git worktree 中启动
```

## 九、优势与局限性

### 优势

- **可靠性**：规则和钩子形成"缰绳与围栏"，使 AI 输出可预测、高质量。
- **可扩展性**：3–7 人小团队可借助智能体线束交付百万行级别的生产系统。
- **面向未来**：底层模型升级时，核心线束（规则、反馈循环、专属技能）依然有效。
- **降低幻觉**：多智能体评估器-优化器循环 + 强制验证门禁显著减少错误。

### 局限性

- **上下文窗口约束**：配置不当的线束会导致"淹没在中间"效应，噪声压倒信号。
- **架构漂移**：AI 生成速度过快可能积累技术债，需要自动化"垃圾回收"机制持续治理。
- **执行风险**：Shell 或网络权限若未妥善沙箱化，存在系统损坏或数据泄露风险。

## 十、常用操作速查

| 操作             | 命令/快捷键                                              |
| -------------- | --------------------------------------------------- |
| 进入计划模式         | `claude --permission-mode plan` 或会话中按 **Shift+Tab** |
| 压缩上下文          | `/compact`                                          |
| 清空会话           | `/clear`                                            |
| 在新 worktree 启动 | `claude -w`                                         |
| 管道输入分析         | `cat error.log \| claude -p "分析崩溃原因"`               |
| 终端直接执行命令       | 输入框输入 `!git status`                                 |
| 中止跑偏任务         | **Esc**（单次中止），**双击 Esc**（查看检查点并回滚）                  |

核心总结

线束工程代表了从**提示词工程**到**环境工程**的范式转变：

- 不要试图通过提示词"编程"模型的每一步行为。
- 而是构建一个**高标准的运行世界**：清晰的规则、可靠的工具、确定性的约束、持续的反馈循环。

模型已经具备智能；线束工程师的任务，是让这份智能在你的领域中可靠地表达。
